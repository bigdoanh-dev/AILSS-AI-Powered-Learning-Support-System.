## Exact proposed request/read contract

All request objects reject additional properties. Application body contains only required strings `professionalTitle` (1–120), `institution` (1–160), `teachingArea` (1–160), `motivation` (20–2000). Normalize NFC, trim outer whitespace, then validate lengths in Unicode code points; preserve internal whitespace. No markup interpretation. Snapshot displayName and masked email from canonical identity server-side, not from caller fields. Do not collect government identifiers, documents, applicant passwords, role, status, verification flags or userId.

Submission and Admin decisions require the existing visible-ASCII Idempotency-Key format, length 1–200. Submission returns 201 with normal data/meta envelope; data contains applicationId (UUID), status SUBMITTED, submittedAt (UTC date-time). Replay returns the historical data and HTTP status even after later review; current status comes from IDN-14.

IDN-14 returns 200 with data null if no application; otherwise applicationId, four submitted fields, displayNameSnapshot, emailMaskedSnapshot, status, submittedAt, decidedAt (nullable), and user-safe result enum PENDING / APPROVED_AWAITING_VERIFICATION / APPROVED_VERIFIED / REJECTED. Approved next action is derived from current canonical role/verification, not from historical submission response. Account authentication failure must not be treated as an empty application.

For this minimum model, one immutable application per account is allowed, including after rejection. Reapplication/edit/withdraw is deferred; rejection UI offers continued Student use, never an unsupported resubmit action. This stronger bound prevents simultaneous active applications and rapid resubmission without another history/cooldown contract.

IDN-15 requires `month` (YYYY-MM, UTC submission month), `shard` (integer 0–15), optional limit (1–100, default 50), optional integrity-protected opaque cursor (16–16384 characters). Unknown query keys rejected. It lists only SUBMITTED, in submittedAt descending/applicationId ascending order; response items use applicationId, displayNameSnapshot, teachingArea, submittedAt, with nextCursor nullable. The Admin UI exposes month/shard selection, initially current UTC month/shard 0; it must not imply that one partition is all pending applications. Old months remain accessible explicitly. Empty filtered pages may have a continuation cursor.

IDN-16 returns the owner-safe application fields plus applicantId, reviewerId nullable and decision enum nullable. No internal free-text notes are collected in this scope. UUID detail misses return 404.

IDN-17 strict body: decision APPROVE or REJECT; currentPassword 1–128 characters. Gateway sends currentPassword only to INT-IDN-02, strips it from the downstream decision body, and transports the resulting server-only proof. It returns 200 historical data {applicationId, status, decidedAt}; rejection does not mutate user role/status. Current password/proof is never stored in command metadata or returned to Web.

Proposed OpenAPI response registration: IDN-13: 201,400,401,403,409,413,422,429,503; IDN-14: 200,401,403,429,503; IDN-15: 200,400,401,403,422,429,503; IDN-16: 200,400,401,403,404,429,503; IDN-17: 200,400,401,403,404,409,413,422,429,503. Reuse the current error envelope. New proposed domain codes: APPLICATION_EXISTS (409), APPLICATION_DECISION_CONFLICT (409), APPLICATION_TARGET_INELIGIBLE (409), APPLICATION_NOT_FOUND (404), APPLICATION_UNAVAILABLE (503), APPLICATION_INVALID_REQUEST (422). Reuse existing INVALID_ACCESS_TOKEN, ADMIN_ROLE_REQUIRED, ADMIN_STEP_UP_FAILED, IDEMPOTENCY_CONFLICT and existing Gateway parsing/size/rate errors where applicable. These are proposed registrations, not assertions about current runtime. No client may handle them as live until registry/OpenAPI and server agree.

## Internal correction and security

Extend INT-IDN-02 action enum with LECTURER_APPLICATION_APPROVE and LECTURER_APPLICATION_REJECT, resource enum with LECTURER_APPLICATION; bind resourceId to applicationId and owner audience to identity-service. Extend shared signing/verification schemas and explicit action/resource/audience compatibility checks. Preserve current course/report combinations, expiry <=30 seconds, Admin user/session/token epoch binding and fail-closed validation. This is current-password reauthentication, not MFA. Do not repurpose COURSE or REPORT for an application.

Identity independently verifies Gateway actor context and the operation-bound proof, then current canonical Admin/session authorization on new commands and replays. Never authorize from UI role, body fields, queue rows or an old JWT alone. Prohibit self-review. Gateway issues proofs only after exact decision validation. Reuse write/Admin rate limiting and existing origin/CSRF/no-store Web protections. Web holds secrets only in the existing secure server session arrangement and ephemeral password input; no tokens, passwords or proofs in browser storage, URLs, logs or application records.

## Cassandra correction and recovery

No JOIN, ALLOW FILTERING or global scan. Proposed new query registrations:

| Query     | Table / primary key                                                                                             | Access and consumers                                                                                                                                                                                                                             |
| --------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Q-IDN-008 | lecturer_application_by_applicant, PRIMARY KEY(applicant_id)                                                    | Canonical application row, UUID application_id, bounded payload, snapshots, SUBMITTED/APPROVED/REJECTED, timestamps, version, reviewer/decision and durable command metadata. One row per account via IF NOT EXISTS. IDN-13/14/16/17 and repair. |
| Q-IDN-009 | lecturer_application_locator_by_id, PRIMARY KEY(application_id)                                                 | Immutable applicationId → applicantId locator. Detail uses exact locator read then exact canonical read, not a database JOIN. IDN-13/16/17 and repair.                                                                                           |
| Q-IDN-010 | pending_lecturer_applications_by_month_shard, PRIMARY KEY((submission_month,shard),submitted_at,application_id) | Bounded review projection; shard = first SHA-256 byte of applicant UUID string modulo 16. IDN-13/15/17 and repair. Canonical exact read validates each candidate.                                                                                |

All new canonical/locator writes and reads LOCAL_QUORUM; conditional writes LOCAL_SERIAL. List consumes at most limit candidate rows per call and returns a cursor over candidates; it does not loop through an unbounded number of stale rows to fill a page.

Explicitly extend existing Q-IDN-007 consumer list with IDN-13/17 and application-repair; reuse its exact-key idempotency/outbox patterns. Add documented `identity_commands_by_due_bucket` under this recovery query: PRIMARY KEY((due_day,shard),next_attempt_at,operation_id), with bounded worker batches, lease owner/until/fence and stable command locator. This is a declared recovery-schema expansion, not an application access pattern hidden in Q-IDN-007. Preserve old consumers. New application journals have no automatic expiry; existing APIs retain their current TTL policy. Persist immutable canonical body fingerprint and historical response; never currentPassword or proof. No automatic retention cleanup is introduced in this pass.

Update Q-IDN-001 consumers for canonical role reads/promotion, Q-IDN-002 for credential marker synchronization and reauth, Q-IDN-003 for every protected operation, Q-IDN-005 operation metadata to explicitly allow role projection maintenance. Q-IDN-006 remains IDN-12's verified-public projection; approval creates none. Register exact consumers in both directions, with IDN-15 canonical hydration using Q-IDN-008, and INT-IDN-02 retaining Q-IDN-001/002/003.

Submission recovery: persist due-bucket repair intent before any canonical write; reserve actor+API+key journal and stable applicationId; canonical applicant row IF NOT EXISTS elects one application. Same key+canonical body replays; changed body conflicts; different key cannot create another application. Finish locator, pending projection, stable audit outbox and historical result before 201. Ambiguous LWT outcomes require exact read-back. A crash before journal creation leaves a harmless repair intent, not an undiscoverable canonical row.

Review recovery: reserve Admin+API+application+key journal after reauth; LWT claim SUBMITTED application/version for one decision operation. Conflicting approve/reject loses with 409. Store durable authorized actor/decision/fingerprint and expected canonical security versions. Application stays SUBMITTED during internal recovery; processing stages are separate metadata, never account/application public statuses.

APPROVE effect: conditional canonical STUDENT + ACTIVE → LECTURER + ACTIVE, lecturerVerified=false, tokenVersion incremented exactly once, securityOperationId set to winning operation. Synchronize credential security marker and Admin role/status projection, then finalize application APPROVED and queue removal; persist audit and historical result. No verified public projection. Use existing security version CAS/read-back conventions; never overwrite a concurrent disable/password/profile operation. A conflicting disable before role CAS terminates with a recoverable conflict; if promotion already committed, recovery records that historical approval without re-enabling a later-disabled account. Repair must recognize durable completion evidence, not repeatedly demand that a user remain forever in the originally approved state. Successful response waits for the logically recoverable sequence to converge; transient recovery returns 503. This is not a claim of cross-partition atomicity.

REJECT effect: conditional application REJECTED, canonical account untouched; remove pending row, audit, persist result. Same-key replay never reruns effects; different-key terminal decision conflicts. Automatic repair executes only the previously authorized durable command; it cannot invent a new decision. Before approving runtime, fault tests must establish that no winning intent is orphaned and concurrent user-security changes cannot be overwritten.

Approval is expressly **not verification**. IDN-12 remains the separate Admin verification action. Promotion invalidates old sessions through the epoch change; Web clears stale session and prompts login. Unverified Lecturer UX explains verification is pending. Learning/Classroom/AI retain their existing server authorization; do not promise capabilities solely from approval. Single-role promotion can remove access to Student-only routes; existing learning records remain, but multi-role participation is deferred and must be made clear before submission.

## Events and Web delivery

Reuse system.audit.requested.v1, producer identity-service, with stable eventId derived from operationId. Formally document actions LECTURER_APPLICATION_SUBMITTED / LECTURER_APPLICATION_APPROVED / LECTURER_APPLICATION_REJECTED, aggregate and target type LECTURER_APPLICATION, UUID applicationId, application version, actorId/type, outcome SUCCESS and requestId. Include no application free text, password, proof or raw email. Publish through prepared/ready outbox only after corresponding durable effect. Do not emit user.status_changed for a role transition or user.registered for an application. No new event type. Notification remains deferred; status read is authoritative.

After runtime acceptance, replace `/auth/register/lecturer` fallback with explanation “Đăng ký để tạo khóa học, tổ chức lớp học và sử dụng AI hỗ trợ chuẩn bị nội dung.” Anonymous visitors receive register/login with an allowlisted return path. Authenticated Students see form → review → submit → `/auth/register/lecturer/status` using IDN-14 only. Preserve fields only in memory, stable key during retries, no fake polling endpoint. Show SUBMITTED “Yêu cầu của bạn đang được xem xét.”; approval requires fresh canonical session and exact verification-aware next action; rejection is respectful and allows continued Student use. Never claim Lecturer creation on submit. Provide an Admin list/detail/decision UI with ephemeral current-password reauth and separate IDN-12 verification action.

Preserve P12.2A NVD AuthLayout, no public header/large footer, restrained animated environment, panel transitions, step progress, focus and reduced-motion support. Client validation mirrors final server constraints. No runtime UI changes are authorized by this document alone.
