# Cassandra migration parity baseline

The ordered registry contains 61 migrations per profile (001–095, with gaps in the numbering). `dev` and `research` each contain exactly that ordered set. The original 58 migration files and their SHA-256 values remain unchanged. Migrations 093–095 are new CQL files in each profile.

## Classification of the six historical differences

| File | Classification            | Decision                                                                                                                                                                                                                                                                                                                           |
| ---- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 001  | Environment configuration | Keep replication factor 1 for the single-node dev cluster and 3 for the research cluster. This is not feature drift.                                                                                                                                                                                                               |
| 023  | Formatting                | Keep both historical checksums. All six course-offering tables and their options are logically identical.                                                                                                                                                                                                                          |
| 024  | Comment only              | Keep both historical checksums. Entitlement and order CQL statements are identical.                                                                                                                                                                                                                                                |
| 033  | Real table-option drift   | The six schedule/reservation tables and their keys/columns agree. Research omitted explicit TWCS compaction for `student_schedule_by_day` and `schedule_reservations_by_expiry_bucket`; migration 093 sets the same TWCS options in both profiles. Other explicit/default compaction differences use the same SizeTiered strategy. |
| 043  | Whitespace                | Keep both historical checksums. Assessment result CQL statements are identical.                                                                                                                                                                                                                                                    |
| 062  | Formatting                | Keep both historical checksums. AI quiz/quota CQL statements are identical.                                                                                                                                                                                                                                                        |

The schedule tables are used by `apps/classroom-service/src/repository.ts`. The other differing product schemas are used by `apps/learning-service/src/offerings/repository.ts`, `apps/learning-service/src/commerce/repository.ts`, `apps/assessment-service/src/repository.ts`, and `apps/ai-service/src/quiz/repository.ts`; course offering and commerce also have phase 7 acceptance scripts. These are shared features, rather than profile-specific experimental tables. Migration 080 contains product experimentation tables in **both** profiles; their presence is historical and is not a parity difference. The current experimentation service keeps assignments in memory, so these tables must not be treated as proof of durable runtime usage. No historical or experimental table is dropped by this reconciliation.

## Bootstrap and populated upgrade

`scripts/dev/bootstrap-cassandra.mjs` reads files in registry order and verifies their profile-specific hashes before applying each CQL file. A new cluster has no schedule tables before migration 033, so migration 093 can apply after the baseline. `CREATE ... IF NOT EXISTS` and `ALTER TABLE ... ADD IF NOT EXISTS` statements can be rerun. The two `ALTER TABLE ... WITH compaction` statements in 093 set deterministic table options and can be rerun with the same values.

Migration 094 creates the `ai_service` keyspace and its `ai_token_usage` table in both profiles. Replication uses `ailss_dc:1` in dev and `ailss_dc:3` in research, matching each profile's existing keyspaces. The partition key `(user_id, usage_day)` bounds partition growth by UTC day, while `(timestamp, usage_id)` retains multiple calls at the same timestamp. The bootstrap grants `svc_ai` access to the new keyspace. Assistant usage writes run asynchronously after provider metadata arrives; a process exit or Cassandra failure can lose a record, so this table is not an exactly-once billing ledger.

Migration 095 adds `ai_service.assistant_response_cache` with identical schema in both profiles. Writes use a configurable TTL (default 86,400 seconds); rows expire in Cassandra. Cache keys hash the request context and caller scope. Cache access failures leave generation available.

For an existing cluster, first take a backup and collect a read-only target snapshot covering schema agreement, table/column/options, population, replication and capacity. Run `node scripts/ci/precheck-populated-migrations.mjs --target-snapshot <path>` and review migration 093's table-option change, including SSTable age and TWCS suitability. The bootstrap runner requires `AILSS_APPROVE_093_COMPACTION=true` when its pre-migration schema inspection finds existing schedule tables that do not already have the target TWCS options. This flag records operator approval; it does not perform the review. An already converged target can rerun without the flag. Do not run the bootstrap against production without the separate deployment procedure.

There is no native migration-history table. The populated-target precheck infers state from schema objects and verifies committed historical checksums; it cannot prove which statements were previously applied. Compare the target's observed schema with the registry and inspect partial migrations before any upgrade. The validator `node scripts/ci/validate-migration-bootstrap-parity.mjs` checks filenames, ordering, hashes, idempotent CREATE/ADD forms, inventory and logical CQL parity. It normalizes only the documented 001 replication and historical 033 compaction differences; migration 093 reconciles the latter in final schema.
